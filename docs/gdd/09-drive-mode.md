## 9. Drive Mode

**Status:** partial

The drive view is the second half of VibeCity's "build it, drive it, build more" loop. It lives at `/<slug>` (REQ-006) and renders the saved city as a three.js scene the author can drive around in. v1 ships an aerial / orbit scaffold so the build / drive round trip can be experienced ahead of a drivable car (REQ-031 onward); the physics, wheel contact, chase camera, and input slices land on top of that scaffold once the segment-based path (REQ-064) and multi-cell footprint plumbing (REQ-059) ship.

This file is the canonical spec for the drive-mode requirements (REQ-031 through REQ-039 plus REQ-053, REQ-054, REQ-055, REQ-066, REQ-067, REQ-068, REQ-069).

## Scene scaffold (REQ-044, REQ-045, REQ-046)

The scene is a raw three.js mount on a canvas the React component owns. The `WebGLRenderer` attaches to the canvas directly so the React tree controls mounting / unmounting. A noon-style lighting rig (ambient plus directional from above and slightly south-east) lights a flat ground plane sized large enough to read past the visible city. Street pieces render as flat colored quads on the grid; buildings render as extruded boxes with per-type heights and colors so the four placeholder primitives form a visible silhouette vocabulary from the orbit view. World coordinates use `CELL_SIZE = 4` to match VibeRacer's world-unit so a saved city is reusable across both projects.

## Camera (REQ-033)

The drive view ships two camera modes selected by whether a car is mounted. An empty city stays in the v1 aerial / orbit framing: a fixed camera tilts down at the city center from a height proportional to `CELL_SIZE` so the empty-state prompt reads against a neutral backdrop centered on the grid origin. A city with at least one street piece engages the chase camera rig in `cameraRig.ts`, which sits `CAMERA_RIG_DISTANCE = CELL_SIZE * 3.5` units behind the car along its forward axis at `CAMERA_RIG_HEIGHT = CELL_SIZE * 1.6` and looks at a target `CAMERA_RIG_LOOK_AHEAD = CELL_SIZE * 1.5` units in front of the car. Both the camera position and the look target ease toward their desired pose each frame via `CAMERA_RIG_POSITION_LERP = 0.12` and `CAMERA_RIG_TARGET_LERP = 0.2` so a sharp turn glides through the camera instead of snapping. The mode is mirrored on the scene root as `data-camera-mode='chase' | 'orbit'` so a test can assert the rig engagement without inspecting the WebGL state. Camera tuning surface (REQ-040) replaces the hard-coded constants with a settings pane in a later slice; v1 ships the chase-far preset only.

## Input (REQ-034, REQ-035)

v1 ships keyboard input as the first input slice (REQ-034). Bindings are declared in `driveControls.ts` as a layout-stable `KeyboardEvent.code` table (WASD plus the four arrow keys cover throttle / brake / steer left / steer right) so the binding map works on QWERTY, AZERTY, and Dvorak without a per-locale rebinding. Listeners attach to `window` so the canvas does not need focus to drive; an in-flight blur clears the pressed-key set so a tab switch does not leave the throttle stuck on. The pressed-key set is exposed as a `data-keys-pressed` attribute on the scene root so a test can assert the listener wiring without inspecting the WebGL scene graph. Touch input (REQ-035) ships as a sibling input source: pointer event listeners attach to `window` (gated on the car-mounted branch like the keyboard handlers) and drive a pair of float-where-you-tap virtual joysticks. Under `dual-stick` (the persisted default per REQ-042), a touch on the left half of the viewport anchors the steering joystick and a touch on the right half anchors the throttle / brake joystick; the steer stick's horizontal axis steers and the throttle stick's vertical axis throttles (up) or brakes (down). Under `single-stick`, any touch anywhere anchors a single joystick whose horizontal axis steers and whose vertical axis throttles / brakes; the second stick stays inactive so only one ring renders. The pure helpers in `touchInput.ts` (`createJoystick` / `beginJoystick` / `moveJoystick` / `endJoystick` / `readJoystick`, `joysticksToInput` mapper, `mergeDriveInputs` per-action OR helper, `joystickForTouch` routing helper, plus `JOYSTICK_RADIUS = 64` and `JOYSTICK_DEADZONE = 0.25` matching VibeRacer values) keep the gesture math fully unit-testable. The integration loop calls `joysticksToInput` each tick and merges the result with the keyboard input via `mergeDriveInputs` so a player can tap touch and hold W at the same time and the integrator just sees throttle on. Touch on an interactive surface (button, link, input, textarea, select) is skipped so a tap on the Resume button inside the pause menu does not also start a steering joystick; `event.preventDefault()` on the gesture-anchoring `pointerdown` blocks the browser from scrolling / pinch-zooming while the player is steering. The first touch is also the user gesture that unlocks the engine audio rig (REQ-068) so a touch-only player still gets engine sound. Visible joystick rings render as fixed-position circles anchored at each active joystick's origin with a smaller filled dot at the thumb position (clamped to `JOYSTICK_RADIUS` along the angle of travel) so the player has a visual anchor for the gesture; the rings unmount when the joystick releases or the pause menu opens. The live joystick activity is mirrored on the scene root as `data-touch-steer-active` / `data-touch-throttle-active` so a test can assert the runtime wiring without inspecting the SVG layer. The Edit CTA at the top right of the scene navigates back to `/<slug>/edit`; the slug label at the top left names the active city.

The integration loop runs at the browser's animation frame cadence and calls into the pure `applyDriveStep(state, input, dt)` helper from `driveControls.ts`. Throttle adds forward acceleration, brake decelerates a forward-moving car and accelerates in reverse from rest, and steering rotates the heading at a rate proportional to current speed (sharper at low speed so a parked car can pivot in place). The car's world-space position and heading are mirrored into `data-car-x`, `data-car-z`, `data-car-heading`, and `data-car-speed` attributes on the scene root so a test can read driving state imperatively. The integration loop and key listeners are gated on the car being mounted; an empty city keeps both dormant so an author cannot accidentally accelerate a car that is not on screen. Off-street penalty (REQ-054), wheel contact (REQ-032), and the chase camera (REQ-033) wait for their own slices.

## Spawn anchor (REQ-036)

The vehicle spawns on a deterministic anchor cell: `(piece.row, piece.col)` of the first placed street piece, or the grid origin `(0, 0)` when no pieces exist. v1 ships the helper `spawnAnchor(pieces)` and a placeholder vehicle (REQ-047) at the anchor position so a builder can see where the car will appear; the vehicle is omitted on an empty grid because the empty-state prompt owns that visual focus. The persisted rotation of the first piece flows through to the vehicle group so a build / drive author can see the orientation the car will face. The earliest v1 release shipped a chevron-shaped marker at this anchor; the placeholder car composition (REQ-047) replaced it in a follow-up slice. The physics that move the car from the spawn anchor (REQ-031) wait for their own slice.

## Empty grid (REQ-053)

When the city has zero pieces and zero buildings the scene renders a friendly "Place a road first" prompt centered on the canvas with an Open editor link back to `/<slug>/edit`. The prompt is a DOM overlay (not a three.js text mesh) so it is screen-reader friendly and does not require a font texture in v1. The overlay declares `role="status"` with `aria-live="polite"` and exposes the `drive-empty-prompt` test id; the underlying three.js scene still renders the ground plane and lighting rig so the empty city does not appear broken.

## HUD (REQ-066)

The drive view ships a minimal HUD as the v1 driver-feedback surface. Two fixed-position overlays render only when a car is mounted and the pause menu is closed: a bottom-left speed readout that shows the live forward speed magnitude as an integer value plus a small horizontal bar that fills from the left as the speed approaches `MAX_SPEED`, and a bottom-right controls hint that lists the five default bindings from `driveControls.ts` (W / Up: throttle, A / Left: steer left, S / Down: brake, D / Right: steer right, Esc: pause). The pure helpers in `driveHud.ts` (`formatSpeed`, `speedFraction`, `speedDirection`, the `HUD_CONTROLS_HINT_LINES` table, the `HUD_SPEED_LABEL` and `HUD_SPEED_UNIT` constants) keep the formatting and the bar fraction math fully unit-testable. The integration loop in `DriveSceneClient.tsx` writes the readout text and the bar `transform: scaleX(...)` imperatively each tick so the React tree does not re-render every frame; the live speed magnitude is also mirrored onto the scene root as `data-hud-speed` / `data-hud-direction` so a test can read the readout state without sampling the WebGL scene graph. The HUD hides while the pause menu is open so the modal owns the click surface (REQ-039); both overlays carry `pointerEvents: 'none'` so they never steal clicks from a future canvas hit-test layer. The unit string is `wu/s` (world units per second) because the v1 integrator is not calibrated to a real-world speed; the label is loud about that so the readout does not lie. REQ-037 explicitly forbids a lap timer, checkpoints, or a race HUD; the v1 HUD ships only driver feedback (speed, direction) and a static binding hint, which does not violate the anti-feature.

## Pause menu (REQ-038, REQ-039)

The drive view ships a single-key pause: pressing Esc on a populated drive scene flips the pause state and renders a modal overlay over the canvas; pressing Esc again (or clicking Resume) closes the menu and the integrator picks up from the same vehicle pose. The state machine lives in `pauseMenu.ts` as a pure module (`PauseState = 'running' | 'paused'` plus `togglePauseState` / `openPauseMenu` / `closePauseMenu` / `isPaused`) so the React surface and the integration loop both read the same vocabulary. The integration tick consults the live state via a ref and skips `applyDriveStep` plus the chase camera rig update while paused; the renderer still draws one frame per tick so the overlay reads against a live canvas, and `lastTimestamp` resets each paused frame so the first resumed delta does not back-integrate the elapsed pause duration. Pressed keys are intentionally NOT cleared on pause so resuming with throttle still down keeps accelerating, matching driver intuition. The Esc listener attaches only when the car is mounted; the empty grid keeps the menu dormant. The pause overlay (`role="dialog"` / `aria-modal="true"` / `data-testid="drive-pause-menu"`) sits at `zIndex: 10` above the slug label and the top-right Edit CTA so it owns the click surface while paused, lays the slug header over a translucent black backdrop, and offers two actions: Resume (an `autoFocus` button so a keyboard / screen-reader user can press Enter to dismiss) and Edit (a `next/link prefetch` to `/<slug>/edit` for REQ-038 so the build / drive author can walk from a paused world straight back to the editor). The pause state is mirrored on the scene root as `data-pause-state="running" | "paused"` so a test can assert the toggle without inspecting the React tree. VibeRacer's lap-timer compensation (which paused / resumed the lap timer around a paused interval) is dropped here because REQ-037 explicitly forbids the lap timer in VibeCity.

## Respawn (REQ-067)

The drive view ships a one-key respawn so a player who tipped off the world, wedged against a building, or simply got turned around can recover without reloading the page. Pressing `R` on a populated drive scene resets the car to the spawn anchor (the same `(piece.row, piece.col)` cell REQ-036 uses on first mount), zeroes the speed, sets the heading from the first piece's persisted rotation, clears the pressed-key set so a held throttle does not relaunch the freshly-spawned car, snaps the chase camera rig to the new pose so the rig does not ease in from the wreck position on the next tick, and refreshes every per-frame data-attribute mirror (`data-car-*`, `data-on-building`, `data-off-street`, `data-hud-*`). The pure helper lives in `respawn.ts` (`RESPAWN_KEY_CODE = 'KeyR'` plus `respawnVehicle(pieces)`) so the unit tests cover the pose math without three.js. The keydown listener is gated on the car being mounted (the empty grid keeps it dormant), short-circuits while the pause menu is open (a paused world cannot teleport the car mid-pause), and uses the same text-target guard as the WASD / Esc handlers so a future input on the drive surface keeps `R`-as-text working. `R` does not collide with any binding in `DEFAULT_KEY_BINDINGS` from `driveControls.ts`; the editor's `R`-for-rotate binding lives in a separate page tree (`/<slug>/edit`). The HUD controls hint (REQ-066) lists `R: respawn` between the steer-right row and the pause row so a first-time visitor sees the binding alongside the rest of the vocabulary. Future settings (REQ-041) may rebind `R` via a settings pane but should preserve the default.

## Off-street penalty (REQ-054)

The drive view ships a cell-level binary off-street penalty that mirrors the building-cell collision (REQ-030, Q-005 default A) so a player who veers off the placed streets feels an immediate slowdown instead of cruising over the empty grid. The pure helpers in `offStreetPenalty.ts` (`streetCellSet`, `isOnStreetCell`, `applyOffStreetPenalty`) keep the cell-coverage and speed math fully unit-testable. The integration loop in `DriveSceneClient.tsx` calls `applyOffStreetPenalty` immediately after `applyDriveStep` and BEFORE the building-cell penalty so the integrator's normal coast / throttle / brake / steering math runs first, then the off-street cap clamps the result, then the building cap clamps tighter if both apply. Tuning lands at `OFF_STREET_PENALTY_MAX_SPEED = CELL_SIZE * 3` (a more permissive cap than the building cap of `CELL_SIZE * 2` so off-road feels lighter than a building hit), `OFF_STREET_PENALTY_MAX_REVERSE_SPEED = CELL_SIZE * 1.5` (half the forward cap so reversing off-road cannot rocket the car backward), and `OFF_STREET_PENALTY_DRAG = CELL_SIZE * 8` (lighter than the building drag of `CELL_SIZE * 12` so the bleed feels firm but more forgiving than a building hit). The street cell set expands multi-cell pieces (mega sweep, hairpin, future arc45 / diagonal once REQ-059 lands) via the shared `pieceFootprintCells` helper from `edit/snapGrid.ts` so a piece with an explicit footprint contributes every cell it covers. The "car cell" is derived from the vehicle's center position via `worldToCell` (nearest-cell rounding) rather than a per-wheel sample because v1 has no wheel contact module yet (REQ-032); per-wheel sampling lands when REQ-032 ships and the four wheel-cell lookups collapse into the same cell-key Set this module already builds. The live off-street flag is mirrored onto the scene root as `data-off-street="true" | "false"` so a test can assert the penalty engages without sampling the speed history.

## Minimap (REQ-069)

The drive view ships a top-right minimap so a player can read the city silhouette and the live car position at a glance. The pure helpers in `driveMinimap.ts` (`minimapBoundsForCity`, `worldToMinimap`, `headingToMinimapDegrees` plus the `MINIMAP_SIZE_PX = 160` viewport size, `MINIMAP_PADDING_CELLS = 1` halo, and the per-layer color constants) keep the bounds projection and heading math fully unit-testable. The bounds helper letterboxes the city's bounding box into the square viewport so the longer axis fills the frame and the shorter axis is centered with even padding; this keeps the on-screen scale uniform regardless of city aspect ratio. The world-to-pixel projection keeps north at the top of the minimap because the world's `+z` is south and SVG's `+y` is down, so a smaller `z` renders at a smaller `y`. The integration loop in `DriveSceneClient.tsx` writes the live `translate(...) rotate(...)` transform onto the SVG car group each tick so the marker tracks the car position and heading without forcing a React re-render; the live coords also mirror onto the scene root as `data-minimap-car-x` / `data-minimap-car-y` / `data-minimap-car-rotation` so a test can read the projection state without inspecting the SVG transform. The minimap panel renders only when `hasVehicle && !showPauseMenu && minimapBounds` so the empty grid keeps the panel hidden (no city footprint to project) and the pause menu owns the click surface (REQ-039). The panel carries `pointerEvents: 'none'` so it never steals clicks from a future canvas hit-test layer. The street pieces render as small piece-brown squares at their footprint cells (so multi-cell pieces show every cell of their footprint via `pieceFootprintWorldCells`); buildings render as olive squares slightly smaller than the cell so the two layers are visually distinct. The player car renders as a heading-rotated red triangle so a player can disambiguate forward direction at a glance. REQ-037 explicitly forbids a lap timer, checkpoints, or a race HUD; the v1 minimap shows only static silhouette plus a player marker, which does not violate the anti-feature.

## Engine audio (REQ-068)

The drive view ships a minimal Web Audio engine rig so a moving car has an audible signature. The pure helpers in `engineAudio.ts` (`engineFrequencyForSpeed`, `engineGainForSpeed`, `ENGINE_IDLE_FREQUENCY_HZ`, `ENGINE_MAX_FREQUENCY_HZ`, `ENGINE_IDLE_GAIN`, `ENGINE_MAX_GAIN`, `ENGINE_FILTER_CUTOFF_HZ`, `ENGINE_SMOOTHING_SECONDS`, `ENGINE_MUTE_KEY_CODE = 'KeyM'`) keep the frequency / gain mapping fully unit-testable; the live runtime lives in `EngineAudioRig` which owns a sawtooth oscillator routed through a lowpass filter (cutoff 1200 Hz) into a gain node clamped well below clipping (peak 0.18) so other future audio sources can layer on top. The rig is built lazily on the first user gesture inside the integration effect (`AudioContext` construction is autoplay-gated by every browser); the `start()` call resumes a suspended context and ramps the gain to the idle level so the resume does not click. Each tick the integration loop calls `rig.update(vehicle.speed)` so the oscillator frequency tracks the live speed via `setTargetAtTime` ramps with `ENGINE_SMOOTHING_SECONDS = 0.08` smoothing, and the gain climbs in step with the pitch via the same constant. Reverse uses the speed magnitude so the engine note climbs the same way in both directions; the v1 rig does not differentiate forward and reverse engine sounds. While the pause menu is open the integration loop calls `rig.update(0)` so the engine falls back to the idle pitch and gain so the menu reads against quiet; resume restores the speed-driven values on the next tick. Respawn (REQ-067) also calls `rig.update(0)` so a player who was at full throttle when they pressed R does not hear the engine note hold over from the wreck. The unmount cleanup branch calls `rig.stop()` which ramps the gain to zero and stops the oscillator; the `AudioContext` is left open so future audio surfaces can layer on top without a fresh resume. The HUD ships a Sound on / Sound off toggle button (`drive-engine-mute-toggle` testid, `aria-pressed` mirroring the live mute state) at the top right of the scene plus an `M: mute engine` line at the end of the controls hint; the M key flips the same toggle as the button. Mute uses `setMuted(true)` which ramps the gain to zero without tearing down the rig so unmute is instant. The live mute state is mirrored on the scene root as `data-engine-audio-muted='true' | 'false'` and the `data-engine-audio-started='true' | 'false'` attribute flips to true once the rig is built so a test can read the rig state without inspecting the AudioContext. The rig is omitted on the empty grid because the drive listener gate (already used by REQ-034 / REQ-039 / REQ-067) keeps the audio context construction dormant on a city with no pieces.

## Race-HUD anti-feature lockdown (REQ-037)

VibeCity is a city-builder loop, not a racing game. The drive surface explicitly forbids a lap timer, checkpoints, lap counters, finish lines, leaderboards, podium standings, or any other race-scoring HUD. The pure module `driveAntiFeatures.ts` exports `RACE_HUD_FORBIDDEN_TERMS` (a lowercase list of race vocabulary that may not appear in any HUD overlay copy, including `lap`, `checkpoint`, `lap timer`, `finish line`, `leaderboard`, `standings`, `podium`) and `RACE_HUD_FORBIDDEN_TESTIDS` (a list of testids prefixed `drive-` that must not exist anywhere on the drive surface, including `drive-lap-timer`, `drive-lap-counter`, `drive-checkpoint`, `drive-checkpoint-banner`, `drive-race-timer`, `drive-finish-line`, `drive-leaderboard`, `drive-standings`). The `containsRaceHudVocabulary(text)` helper does a case-insensitive whole-word match (single-word terms split on alphanumeric boundaries so `elapsed` does not match `lap`; multi-word terms match contiguous lowercase substrings) so a copy edit cannot smuggle race vocabulary into a player-visible string. The unit tests assert that every line of `HUD_CONTROLS_HINT_LINES` plus the `HUD_SPEED_LABEL` and `HUD_SPEED_UNIT` strings stay clean of the forbidden vocabulary; the e2e suite asserts each forbidden testid resolves to zero elements on both the scaffold and empty-state drive specs, regardless of whether a car is mounted, so a future regression that ships a race surface before the car-mounted gate also trips. The v1 HUD ships only driver feedback (speed, direction) and a static binding hint, plus the minimap silhouette and the engine-mute toggle, none of which violate the anti-feature.

## Out of scope for v1

- Lap timer, checkpoints, race HUD (REQ-037 anti-feature, actively enforced via the Race-HUD lockdown section above).
- Settings pane (REQ-040 onward).
- Wheel contact (REQ-032 partial). The per-wheel on-street decision now lands via `wheelOnStreet` reading the multi-locator substrate. The per-piece sampled centerlines (F-003 / F-004) and the closest-candidate distance pick stay deferred.
- Smooth client-side transition between drive and edit (REQ-055). The v1 round trip uses a standard `next/link` navigation; the prefetch that lands here makes Q-002 default C cheap to wire in a follow-up slice.
